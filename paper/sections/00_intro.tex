\section{Introduction}
\label{sec:intro}

Mixture-of-Experts (MoE) architectures have emerged as a prominent approach for scaling Large Language Models (LLMs) to hundreds of billions of parameters~\cite{shazeer2017outrageously,fedus2022switch, jiang2024mixtral,dai2024deepseekmoe}.
By dynamically routing each token to only a sparse subset of experts, MoE models substantially increase model capacity while keeping per-token computation bounded~\cite{du2022glam,rajbhandari2022deepspeedmoe}.
However, sparse activation reduces computation rather than model storage: although only a small number of experts are activated for each token, the runtime must still make the entire expert pool available for routing.
As MoE models scale, expert weights can therefore dominate the memory footprint and impose substantial pressure on accelerator High-Bandwidth Memory (HBM).
To serve such models on memory-constrained accelerators, \textbf{expert offloading} has become an important strategy: the runtime keeps non-expert layers and a bounded subset of frequently used experts in local HBM, while fetching non-resident experts from host memory on demand~\cite{hwang2024pregated,xue2024moeinfinity,li2026commitmoe}.
Expert offloading makes otherwise memory-infeasible MoE models deployable on limited-HBM devices, but introduces dynamic expert movement into the inference critical path.

To make expert offloading practical, prior systems reduce its data-movement overhead through expert caching, routing-aware prediction and prefetching, and transfer--computation overlap~\cite{hwang2024pregated,kong2024swapmoe,cao2025moelightning,fang2025klotski,xue2024moeinfinity}. 
These techniques reduce the frequency of host-to-device transfers or hide part of their latency, substantially improving the efficiency of offloaded MoE inference. 
However, they do not eliminate the inherent execution dynamism introduced by expert offloading. 
Routing-driven cache misses can still trigger expert loading, eviction, and replacement, causing the set of HBM-resident experts to evolve across decoding steps. 
More importantly, loading and replacing experts in a bounded HBM cache can change the mapping between logical experts and their physical weight locations across decoding steps.
Thus, existing data-movement optimizations improve which experts are moved and when they are moved, but they do not eliminate runtime changes in expert residency or logical-to-physical weight bindings.

Such runtime changes can be naturally accommodated under eager execution, where the host resolves the current expert placement and dispatches the corresponding kernels at each decoding step. 
This flexibility, however, comes at a substantial performance cost. 
Autoregressive decoding repeatedly executes a largely recurring sequence of fine-grained accelerator kernels, and launching these kernels individually incurs repeated host-side scheduling, dispatch, and synchronization overhead. 
\textbf{Graph replay} mitigates this overhead by capturing the recurring execution sequence once and replaying it as a unit, thereby reducing host-induced gaps between kernel executions~\cite{kwon2020nimble,ye2025flashinfer}. 

As shown in Figure~\ref{fig:graph_breakdown}, graph replay reduces average decode latency by approximately 75\% across four workloads, from 133.7--137.4~ms/token under eager execution to 32.6--33.6~ms/token, while device execution time remains nearly unchanged. 
This result indicates that most of the improvement comes from eliminating host-induced device idle time rather than accelerating the underlying kernels. Therefore, falling back to eager execution is not merely a compatibility inconvenience; it forfeits a major source of decoding efficiency.

However, these efficiency gains rely on a \textbf{replay-stable execution state}, in which the captured execution structure and graph-visible memory bindings remain valid across replays. 
Dynamic expert offloading creates a fundamental tension with this requirement. 
When routing-driven cache misses trigger expert replacement, the same logical expert may be served from different physical weight locations across decoding steps, changing the logical-to-physical binding observed by captured computation. 
Such binding changes prevent the runtime from safely reusing the captured execution state unless it repairs the affected graph state or reintroduces eager intervention, both of which erode the host-overhead savings of graph replay. 
The central challenge is thus to \textbf{preserve graph replay while allowing expert residency and physical placement to evolve dynamically under a bounded HBM budget}.

Existing systems address the two sides of this tension largely in isolation. 
Expert-offloading systems optimize \emph{what changes} at runtime---which experts remain resident, which experts are transferred, and when those transfers occur---through caching, prediction, prefetching, and transfer--computation overlap~\cite{hwang2024pregated,kong2024swapmoe,cao2025moelightning,fang2025klotski}. 
These techniques improve expert availability under constrained memory, but dynamic replacement and the resulting logical-to-physical bindings remain part of the runtime-managed execution state. 
In contrast, graph-compatible inference runtimes focus on \emph{what must remain reusable}, stabilizing graph-visible workspaces, metadata, and execution configurations so that captured computation can be replayed efficiently~\cite{ye2025flashinfer}. 
However, such mechanisms do not virtualize a dynamically replaceable expert working set within a bounded HBM budget. 
Consequently, neither line of work provides an execution abstraction that simultaneously hides dynamic expert replacement from captured computation and preserves efficient graph replay.

Our key insight is to \textbf{separate what graph replay needs to keep stable from what expert offloading needs to change}. 
Expert offloading requires the resident expert set and its placement to evolve with runtime routing, whereas replayability fundamentally depends on keeping the graph-visible execution interface valid across replays. 
This distinction allows us to decouple \emph{logical expert identity} from \emph{graph-visible physical storage}: the physical storage exposed to captured computation can remain stable, while the association between logical experts and resident weights evolves between replays to reflect the current resident set.
Under this abstraction, expert replacement becomes an \emph{inter-replay state transition} rather than a change to the graph-visible execution interface. 
Dynamic expert residency can therefore coexist with reusable graph execution without requiring all experts to remain permanently resident in HBM.

Realizing this abstraction introduces three systems challenges. 
\textbf{First, dynamic expert staging must be separated from captured computation without changing MoE execution semantics.} 
Conventional fused MoE implementations tightly couple routing, expert selection, and expert computation, leaving no explicit execution boundary at which routing-dependent placement decisions and weight transfers can occur outside the captured region while preserving the tensors and routing decisions consumed by subsequent computation. \textbf{Second, dynamically reused expert storage must remain correct under asynchronous transfer and computation.} Replacing an expert too early can overwrite weights still being consumed by in-flight computation, whereas exposing a newly assigned location before its transfer completes can cause captured computation to observe incomplete or incorrect weights. \textbf{Third, execution must remain exact when the routed expert working set exceeds the available HBM capacity.} Requiring all active experts to reside simultaneously would violate the memory budget, while dropping experts or approximating their outputs would alter model semantics. The runtime must therefore bound physical residency without sacrificing correctness, while still retaining opportunities to overlap expert transfer with computation.




Our goal is to preserve graph replay while allowing the resident expert set to
change within a fixed HBM budget.  The key observation is that expert
\emph{identity} may change without changing the addresses consumed by captured
kernels.  A captured MoE computation does not need each logical expert to keep
its original allocation; it needs fixed physical storage containing the right
weights and a consistent logical-to-physical mapping at replay time.  This
observation turns dynamic residency into an inter-replay state transition:
weight contents and mapping values may be updated at an explicit replay
boundary, while the slot tensors and mapping buffers visible to the graph keep
their addresses.  It also separates the data plane that enforces residency
from the control policy that prioritizes expert placement.

Realizing this separation raises three challenges.  First, the fused MoE
operator hides the routing decision inside an opaque computation, leaving no
graph-visible boundary at which data-dependent staging can legally execute;
exposing such a boundary must not change routing or the tensors passed between
captured regions.  Second, asynchronous transfers and expert computation share
the same bounded slot bank.  A new load must not overwrite a slot used by
in-flight compute, and a mapping must not expose a new owner before its transfer
has completed.  Third, a prefill or mixed batch can activate more experts than
the slot bank can hold simultaneously.  Full residency would violate the HBM
budget, while dropping routed experts or approximating their outputs would
change model semantics.  The runtime must therefore execute an oversized
working set exactly in capacity-bounded phases while retaining opportunities
to overlap transfer and computation.

We present \system, a graph-compatible expert-offloading data plane for
vLLM-Ascend.  \system decomposes the opaque MoE forward path into a captured
router, an eager staging seam, and a captured expert MLP.  At the seam, it reads
the active expert set, applies a placement plan, loads misses into a
preallocated slot bank, and updates a persistent logical-to-physical mapping in
place; the captured MLP continues to consume the same slot and metadata
addresses.  Each slot carries an owner and version, and transfer and compute
events protect that ownership until all users of the version have completed.
When an active set exceeds capacity, \system partitions routed token-expert
pairs into exact waves, stages and computes one bounded wave at a time, and
restores outputs to their original token positions.  Multiple staging buffers
permit the next wave's transfers to overlap the current wave's compute.  An
HBM- and KV-aware startup configuration selects resident layers and slot
capacity, while a policy-neutral placement-plan interface allows external
controllers to reuse the same data plane.

In summary, this paper makes four contributions:

\begin{itemize}
  \item We characterize the address-binding conflict between dynamic expert
    residency and accelerator graph replay, and derive the requirements for a
    replay-stable offloading data plane (\S\ref{sec:background}).
  \item We design \system's three-stage decomposition with a captured router,
    eager staging seam, and captured MLP, together with fixed-slot expert
    virtualization.  These mechanisms move
    data-dependent placement outside captured regions while preserving stable
    graph-visible addresses (\S\S\ref{sec:design}--\ref{sec:implementation}).
  \item We introduce a versioned, compute-protected slot lifecycle and exact
    capacity-bounded wave execution for working sets that exceed slot capacity
    (\S\S\ref{sec:design}--\ref{sec:implementation}).
  \item We implement \system as a vLLM-Ascend platform plugin and define a
    graph-only evaluation methodology that records graph execution, HBM use,
    expert transfers, and service metrics while rejecting eager fallback as a
    successful run (\S\ref{sec:evaluation}).
\end{itemize}
